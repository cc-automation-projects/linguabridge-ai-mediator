Чтобы перевести проект **LinguaBridge AI Mediator** из состояния «отличный прототип/учебный проект» в категорию **«Enterprise Production-Ready»** (уровня крупных банков, телекома или финтеха), необходимо внедрить ряд архитектурных и инженерных улучшений. 

Ниже приведен исчерпывающий список доработок, разделенный по доменам, с конкретными примерами кода и конфигураций, которые устраняют скрытые риски масштабирования.

### 1. Архитектура: Разделение ответственности (ML Inference Server)

**Проблема:** В текущей архитектуре Celery-воркеры одновременно обрабатывают HTTP-логику, скачивают файлы из S3, делают HTTP-запросы в amoCRM и *локально* запускают тяжелые ML-модели (NLLB, Whisper). Это приводит к конкуренции за ресурсы (CPU/RAM/GPU) и усложняет масштабирование. Если вам нужно больше воркеров для обработки вебхуков, вы вынуждены дублировать и тяжелые ML-модели в памяти.

**Решение:** Выделить ML-инференс в отдельный микросервис (Inference Server).
*   **Как это выглядит:** Celery-воркеры становятся "тонкими". Они только готовят данные (скачивают из S3, маскируют PII) и отправляют RPC/HTTP-запрос на внутренний ML-сервис.
*   **Инструменты:** **Triton Inference Server** (от NVIDIA, стандарт индустрии) или простой **FastAPI + vLLM** сервис, развернутый на выделенных GPU-нодах.
*   **Выгода:** Вы можете масштабировать Celery-воркеры (CPU) независимо от ML-сервиса (GPU).

### 2. Код и тестируемость: Отказ от глобальных синглтонов в пользу Dependency Injection (DI)

**Проблема:** В текущем коде мы используем глобальные синглтоны (`s3_service = S3Service()`, `nllb_translator = NLLBTranslator()`). Это антипаттерн для тестирования: чтобы замокать S3 в юнит-тесте, приходится использовать грязные хаки через `unittest.mock.patch`, что делает тесты хрупкими.

**Решение:** Внедрить контейнер зависимостей (DI).
*   **Инструменты:** Библиотека **`dishka`** (современный, быстрый DI для Python/Asyncio) или встроенный `Depends` во FastAPI.
*   **Пример реализации:**
  ```python
  from dishka import Provider, Scope, provide
  from app.infrastructure.s3 import S3Service
  from app.ml.nllb_translator import NLLBTranslator

  class AppProvider(Provider):
      scope = Scope.APP
      
      @provide
      def get_s3_service(self) -> S3Service:
          return S3Service()
          
      @provide
      def get_nllb_translator(self) -> NLLBTranslator:
          return NLLBTranslator()

  # В FastAPI:
  @router.post("/webhook")
  async def handle_webhook(
      request: Request, 
      translator: Annotated[NLLBTranslator, Depends()], # Внедряется автоматически
      s3: Annotated[S3Service, Depends()]
  ):
      # ... логика ...
  ```
*   **Выгода:** Юнит-тесты становятся тривиальными. Вы просто передаете Mock-объекты в конструкторы, без магии `patch`.

### 3. База данных: Миграции вместо сырых SQL-скриптов

**Проблема:** Мы создали таблицы через `init-db/01-init.sql`. В реальном продакшене изменение схемы БД (добавление индекса, нового поля) должно быть версионированным, обратимым и выполняемым без даунтайма.

**Решение:** Внедрить **Alembic** для управления миграциями SQLAlchemy.
*   **Действие:** 
  1. Добавить `alembic` в `pyproject.toml`.
  2. Инициализировать: `alembic init alembic`.
  3. Описать модели через SQLAlchemy 2.0 (Async).
  4. Генерировать миграции: `alembic revision --autogenerate -m "add translation_audit table"`.
  5. Применять при старте приложения или через CI/CD пайплайн: `alembic upgrade head`.

### 4. Надежность: Продвинутый Rate Limiting для внешних API

**Проблема:** amoCRM имеет жесткие лимиты (например, 7 запросов в секунду). Даже с Circuit Breaker, если Celery внезапно обработает 50 сообщений, мы получим массовые `429 Too Many Requests`, что может привести к временной блокировке IP со стороны Яндекса/amoCRM.

**Решение:** Добавить Token Bucket Rate Limiter на уровне клиента amoCRM.
*   **Инструменты:** `aiolimiter` или Redis-based rate limiter.
*   **Пример:**
  ```python
  from aiolimiter import AsyncLimiter

  class AmoCRMClient:
      def __init__(self):
          # Максимум 6 запросов в секунду (с запасом от лимита в 7)
          self.rate_limiter = AsyncLimiter(6, 1) 
          
      async def _make_request_async(self, method: str, endpoint: str, **kwargs):
          async with self.rate_limiter: # Ждет, если лимит исчерпан, не роняя задачу
              # ... логика запроса с Circuit Breaker ...
  ```

### 5. Безопасность и Комплаенс (152-ФЗ): Глубокая защита

**Проблема:** Хранение секретов в `.env` и потенциальная утечка PII в логи (если Presidio что-то пропустит).

**Решение:**
1. **Управление секретами:** Перейти от `.env` к **Yandex Lockbox** или **HashiCorp Vault**. Приложение при старте забирает секреты по защищенному каналу.
2. **Двойной контроль PII в логах:** Написать кастомный процессор для `structlog`, который проверяет *уже отформатированную строку лога* на наличие паттернов (телефоны, карты) прямо перед записью в stdout/файл. Это последний рубеж обороны.
   ```python
   def pii_log_scrubber(logger, method_name, event_dict):
       # Простая проверка перед записью лога
       text_to_log = str(event_dict)
       if re.search(r'\b\d{4}\s?\d{4}\s?\d{4}\s?\d{4}\b', text_to_log):
           event_dict["warning"] = "POTENTIAL PII LEAK IN LOG SCRUBBED"
           # Здесь можно заменить найденное на [REDACTED]
       return event_dict
   ```
3. **Шифрование данных:** Включить Server-Side Encryption (SSE) для бакета MinIO/S3 и шифрование дисков PostgreSQL.

### 6. ML и Качество данных: Передача контекста в NLLB

**Проблема:** В текущем коде мы сохраняем контекст в Redis (`context_manager`), но **не передаем его** в модель NLLB. Из-за этого модель не знает, что "он" в текущей фразе относится к "патенту" из предыдущей фразы, что снижает качество перевода местоимений.

**Решение:** Форматировать промпт для NLLB с использованием истории диалога.
*   **Действие:** В `nllb_translator.py` перед вызовом `model.generate` формировать входную строку вида:
  ```text
  [Контекст диалога]:
  Клиент: Менга прописка керак. (Мне нужна прописка)
  Оператор: Сизга янги манзил керакми? (Вам нужен новый адрес?)
  
  [Текущая фраза для перевода]:
  Ҳа, мен янги манзилга кўчдим.
  ```
  *Примечание:* NLLB лучше всего работает, если контекст подается на исходном языке, а целевой язык строго задается через `forced_bos_token_id`.

### 7. Инфраструктура и DevOps: Переход от Docker Compose к Kubernetes (K8s)

**Проблема:** `docker-compose` идеален для локальной разработки, но не для продакшена. Нет самовосстановления при падении ноды, нет грамотного управления секретами и GPU-ресурсами.

**Решение:** Описать базовые манифесты Kubernetes (или Helm Chart).
*   **Ключевые моменты для K8s:**
  1. **Resource Limits:** Жесткое ограничение CPU/RAM для воркеров, чтобы один "съевший" память Whisper не убил весь под.
  2. **GPU Tolerations:** Для пода с ML-моделями указать `tolerations` и `nodeSelector`, чтобы он гарантированно попадал на ноду с видеокартой.
  3. **Shared Memory:** Критически важно для PyTorch. В `deployment.yaml` добавить:
     ```yaml
     containers:
       - name: ml-worker
         volumeMounts:
           - mountPath: /dev/shm
             name: dshm
     volumes:
       - name: dshm
         emptyDir:
           medium: Memory
           sizeLimit: 2Gi # Минимум 2GB!
     ```
  4. **Liveness/Readiness Probes:** Настроить проверки здоровья, чтобы K8s знал, когда модель загрузилась и готова принимать трафик (Readiness), и когда под завис (Liveness).

### 8. CI/CD Пайплайн (Автоматизация доставки)

**Проблема:** Ручной запуск тестов и деплой.

**Решение:** Настроить `.github/workflows/ci.yml` или `.gitlab-ci.yml`, который делает следующее при каждом Push в `main`:
1. `poetry install` и `poetry run ruff check .` (Линтинг).
2. `poetry run mypy app/` (Статический анализ типов).
3. `poetry run pytest tests/ --cov=app` (Тесты с проверкой покрытия кода > 80%).
4. Сборка Docker-образа с тегом `git-commit-sha`.
5. Сканирование образа на уязвимости (Trivy).
6. Push образа в Container Registry (Yandex Container Registry / Docker Hub).

### 🗺️ Приоритетный план доработок (Roadmap to Production)

Если вы готовите это к реальному внедрению, делайте в таком порядке:

1. **Неделя 1: Безопасность и База.** Внедрить Alembic для БД, настроить Yandex Lockbox для секретов, добавить двойную проверку PII в логах.
2. **Неделя 2: Надежность.** Добавить `aiolimiter` для amoCRM, настроить Dead Letter Queue (DLQ) в Celery для необработанных сообщений, дописать передачу контекста в NLLB.
3. **Неделя 3: Архитектура и Тесты.** Рефакторинг на Dependency Injection (`dishka`), написание E2E-тестов с моками внешних API.
4. **Неделя 4: Инфраструктура.** Написание Helm-чарта или K8s манифестов с правильными лимитами ресурсов, `shm_size` и настройка CI/CD пайплайна.
