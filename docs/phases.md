# ДЕТАЛЬНЫЙ ПЛАН РЕАЛИЗАЦИИ: LinguaBridge AI Mediator

## ЭТАП 1: Инфраструктура, Ingestion и Детекция языка (Недели 1-2)
*Цель: Создать надежный, масштабируемый шлюз приема сообщений через паттерн Channel Adapter и обеспечить мгновенное определение языка до начала тяжелой ML-обработки. Приоритет каналов: MAX → VK → Telegram.*

### Подзадача 1.1: Развертывание базовой инфраструктуры и брокера сообщений
- **Инструменты:** Docker Compose, PostgreSQL 15, Redis 7 (с persistence AOF), RabbitMQ, MinIO (S3-совместимое хранилище).
- **Реализация:** 
  - Настройка `docker-compose.yml` с healthcheck-ами для всех сервисов.
  - Конфигурация Celery с RabbitMQ в качестве брокера и PostgreSQL в качестве бэкенда результатов (result backend).
  - Настройка политик жизненного цикла (Lifecycle) в MinIO для автоматического удаления сырых аудиофайлов через 7 дней (соблюдение 152-ФЗ).
- **Действие:** Написание скрипта инициализации БД и создание очередей: `translate_text_queue` (высокий приоритет) и `translate_voice_queue` (низкий приоритет, так как тяжелее).

### Подзадача 1.2: Мультиканальный Ingestion через паттерн Channel Adapter
- **Инструменты:** FastAPI (для webhook-ов), `httpx` (асинхронный HTTP-клиент), `pydantic`, `ffmpeg-python`.
- **Реализация паттерна Channel Adapter:** Создание унифицированной модели `IncomingMessage`, которая абстрагирует различия между каналами:
  ```python
  class IncomingMessage(BaseModel):
      channel: Literal["max", "vk", "telegram"]
      user_id: str
      chat_id: str
      message_id: str
      text: Optional[str] = None
      audio_file_id: Optional[str] = None
      media_type: Optional[Literal["voice", "video_note"]] = None
      timestamp: datetime
      raw_payload: dict  # Оригинальный payload для дебага
  ```
- **Приоритет реализации адаптеров:**

  **А) Адаптер для MAX (Приоритет 1):**
  - **Инструменты:** FastAPI, `httpx`, Pydantic (схемы на основе https://dev.max.ru/docs).
  - **Реализация:** 
    - Создание роутера `/webhooks/max/update` для приема webhook-ов от MAX.
    - Класс `MaxClient` с методами `send_text()`, `send_voice()`, `download_file()`.
    - Обработка специфичных для MAX типов сообщений: голосовые, "кружочки" (video_note), фото, документы.
    - Конвертация TTS-ответов из `.wav` (Silero) в `.ogg` (Opus) через `ffmpeg` перед отправкой в MAX.
  - **Действие:** Настройка rate limiter (через `slowapi` или Redis-based) для соблюдения лимитов MAX API (30 msg/sec на бота).

  **Б) Адаптер для VK (Приоритет 2):**
  - **Инструменты:** `vk_api` или `vk-api-async`, FastAPI (для webhook-ов) или Long Polling.
  - **Реализация:**
    - Создание роутера `/webhooks/vk/callback` или настройка Long Polling.
    - Класс `VKClient` с методами отправки сообщений и загрузки медиа.
    - Обработка специфичных для VK типов: `audio_message` (голосовые), `doc`, `photo`.
    - Маппинг `peer_id` и `from_id` в единую модель `IncomingMessage`.
  - **Действие:** Настройка подтверждения webhook-а (`type: "confirmation"`) и обработка `message_new` событий.

  **В) Адаптер для Telegram (Приоритет 3):**
  - **Инструменты:** `aiogram 3.x`, `httpx`.
  - **Реализация:**
    - Создание роутера `/webhooks/telegram` для приема webhook-ов.
    - Использование `aiogram` для отправки сообщений и скачивания файлов через `bot.download_file()`.
    - Обработка `Voice`, `VideoNote`, `Photo`, `Document`.
  - **Действие:** Настройка FSM (Finite State Machine) в Redis для управления состояниями диалога (если потребуется).

### Подзадача 1.3: Мгновенная детекция языка и базовое PII-маскирование
- **Инструменты:** `fasttext` (модель `lid.176.bin`), `presidio-analyzer`, `presidio-anonymizer`.
- **Реализация:** 
  - Загрузка модели FastText в память при старте воркера. Обеспечение времени отклика < 50 мс.
  - Настройка `presidio` с кастомными паттернами для РФ: `RU_PASSPORT` (серия и номер), `RU_MIGRATION_CARD` (формат миграционной карты), `RU_PHONE`, `RU_SNILS`.
  - Специфика для каналов: 
    - MAX: часто пишут кириллицей (узбекский/таджикский в кириллице) — убедиться, что FastText корректно определяет.
    - VK: поддержка латиницы и кириллицы.
    - Telegram: поддержка emoji и смешанных языков.
- **Действие:** Создание middleware-функции `sanitize_and_detect(text)`, которая возвращает кортеж `(detected_lang_code, masked_text)`. **Критически важно:** маскирование применяется *до* сохранения текста в PostgreSQL или отправки в очередь Celery.

## ЭТАП 2: Локальный ML-пайплайн (NLLB + Whisper) (Недели 3-4)
*Цель: Обеспечить качественный, быстрый и приватный перевод без выхода в публичные облака, с учетом отраслевой специфики.*

### Подзадача 2.1: Развертывание и оптимизация NLLB-200
- **Инструменты:** `transformers`, `bitsandbytes` (для 8-bit квантования), `torch`.
- **Реализация:** 
  - Загрузка модели `facebook/nllb-200-distilled-600M` (оптимальный баланс скорости и качества для low-resource языков).
  - Применение квантования `load_in_8bit=True` для снижения потребления VRAM на 40-50% без критической потери точности.
  - Настройка `forced_bos_token_id` для строгого указания целевого языка перевода (например, `rus_Cyrl`).
  - Поддержка языков: `tg` (таджикский), `uz` (узбекский), `ky` (киргизский), `zh` (китайский), `en` (английский), `ru` (русский).
- **Действие:** Реализация асинхронного сервиса `NLLBService` с пулом инференса, чтобы избежать блокировки event loop при генерации.

### Подзадача 2.2: Интеграция Faster-Whisper для голосовых сообщений
- **Инструменты:** `faster-whisper`, `ctranslate2`.
- **Реализация:** 
  - Использование модели `large-v3-turbo` или `medium` с `compute_type="int8"`.
  - Обязательная активация `vad_filter=True` и настройка `vad_parameters` (например, `min_silence_duration_ms=500`) для игнорирования фонового шума (стройка, рынок) и ускорения обработки.
  - Специфика для каналов:
    - MAX: аудио приходит в `.ogg` (Opus) — прямая подача в Whisper.
    - VK: `audio_message` в `.ogg` — прямая подача.
    - Telegram: `voice` в `.ogg` — прямая подача.
- **Действие:** Создание воркера, который принимает `s3_key` аудио, скачивает его, прогоняет через Whisper и возвращает список сегментов с таймкодами и `confidence_score`. Если `confidence_score < 0.6`, система помечает транскрипт как "Ненадежный".

### Подзадача 2.3: Движок Terminology Override (Пост-процессинг)
- **Инструменты:** `ahocorasick` (библиотека `pyahocorasick` для сверхбыстрого поиска подстрок) или кастомный Trie.
- **Реализация:** 
  - Загрузка отраслевого словаря (JSON/PostgreSQL) в память воркера. Пример: `{"разрешение на работу": "патент", "прописка": "миграционный учет", "регистрация по месту жительства": "миграционный учет"}`.
  - Алгоритм проверяет переведенный NLLB текст и принудительно заменяет общие фразы на утвержденные термины, сохраняя грамматическое согласование (насколько это возможно) или заменяя целые фразы-шаблоны.
- **Действие:** Интеграция этого шага как обязательного финального этапа перед отправкой текста оператору.

## ЭТАП 3: Интеграция с amoCRM и Управление контекстом (Недели 5-6)
*Цель: Бесшовно встроить переводчика в рабочий процесс оператора, обеспечивая его полным контекстом диалога.*

### Подзадача 3.1: Асинхронный клиент amoCRM с Circuit Breaker
- **Инструменты:** `httpx`, `pybreaker`.
- **Реализация:** 
  - Настройка `pybreaker.CircuitBreaker(fail_max=3, reset_timeout=60)` для всех методов amoCRM.
  - Реализация методов: `find_or_create_lead(phone, channel)`, `add_note(deal_id, text)`, `update_contact_tags(deal_id, ["migrant_uz", "channel_max"])`.
  - Маппинг каналов: 
    - Если `channel == "max"` → тег `Источник: MAX`.
    - Если `channel == "vk"` → тег `Источник: VK`.
    - Если `channel == "telegram"` → тег `Источник: Telegram`.
- **Действие:** Обработка специфичных ошибок amoCRM (когда API возвращает 200 OK, но с `{"status": "error"}` в теле). При срабатывании Circuit Breaker сообщение возвращается в очередь Celery с экспоненциальной задержкой.

### Подзадача 3.2: Управление контекстом диалога (Context Window Management)
- **Инструменты:** Redis, Pydantic.
- **Реализация:** Создание строго типизированной модели `ConversationContext`:
  ```python
  class ConversationTurn(BaseModel):
      role: Literal["client", "operator"]
      original_lang: str
      original_text: str
      translated_text: str

  class ConversationContext(BaseModel):
      user_id: str
      channel: Literal["max", "vk", "telegram"]
      turns: list[ConversationTurn] = Field(max_items=10) # Храним последние 10 реплик
  ```
- **Действие:** Перед отправкой текста в NLLB, система извлекает контекст из Redis и формирует промпт в формате Few-Shot: *"Переведи следующее сообщение, учитывая этот контекст диалога: [контекст]. Сообщение: [текущий текст]"*. Это резко повышает точность перевода местоимений и разговорных фраз.

### Подзадача 3.3: Форматирование вывода для оператора (UI/UX)
- **Реализация:** Формирование богатого текста примечания в amoCRM:
  ```text
  🌐 [Перевод AI] Канал: MAX | Язык: Узбекский (Уверенность: 98%)
  📝 Текст: "Здравствуйте, мой патент истекает 15 числа, как его продлить?"
  ---
  🔒 [Оригинал для проверки]: "Salom, mening patentim 15-kuni tugaydi, qanday qilib uni uzaytirishim mumkin?"
  ```
- **Действие:** Реализация логики, при которой оператор видит в первую очередь русский перевод, но имеет возможность развернуть (или увидеть в истории) оригинал для разрешения спорных ситуаций.

## ЭТАП 4: Голосовой тракт, TTS и Безопасность (Недели 7-8)
*Цель: Обеспечить полноценную поддержку голосового общения и защиту уязвимой категории клиентов от мошенничества.*

### Подзадача 4.1: Интеграция Silero TTS для ответов
- **Инструменты:** `silero-models`, `torchaudio`, `ffmpeg-python`.
- **Реализация:** 
  - Загрузка предварительно обученных голосовых моделей для целевых языков (или использование мультиязычных голосов Silero).
  - Настройка параметров `sample_rate=24000` и `speaker` для обеспечения естественного, не "роботизированного" звучания.
  - Конвертация аудио в зависимости от канала:
    - MAX: `.wav` → `.ogg` (Opus) через `ffmpeg`.
    - VK: `.wav` → `.ogg` (Opus).
    - Telegram: `.wav` → `.ogg` (Opus).
- **Действие:** Создание асинхронного сервиса, который принимает текст от оператора, генерирует аудио, конвертирует его в нужный формат и возвращает `file_id` или `s3_key` для отправки ботом.

### Подзадача 4.2: Эвристический Fraud Detector (Детектор мошенничества)
- **Инструменты:** Кастомный класс на базе Regex + легковесная классификация (опционально `ai-forever/ruRoberta-small`).
- **Реализация:** 
  - Проверка *переведенного* текста оператора и *оригинального* текста клиента на наличие триггеров: "переведи на карту", "безопасный счет", "код из смс", "решу вопрос с полицией за деньги".
  - Специфика для каналов:
    - MAX: проверка на мошеннические схемы, связанные с миграционными услугами.
    - VK: проверка на фишинговые ссылки.
    - Telegram: проверка на крипто-мошенничество.
- **Действие:** Если скор мошенничества > 0.8, система не блокирует диалог, но:
  1. Добавляет в примечание amoCRM красный флаг: `🚨 ВНИМАНИЕ: Обнаружены маркеры мошенничества!`.
  2. Отправляет мгновенное уведомление супервайзеру в Telegram.

### Подзадача 4.3: Предобработка аудио (Шумоподавление)
- **Инструменты:** `noisereduce` или встроенные средства `ffmpeg`.
- **Реализация:** Перед подачей байтов аудио в Faster-Whisper, применение фильтра для снижения фонового шума (актуально для записей с улицы или производства).
- **Действие:** Интеграция этого шага в пайплайн обработки голосовых сообщений для снижения WER (Word Error Rate) на 10-15%.

## ЭТАП 5: Production Hardening и Fine-Tuning (Недели 9-10)
*Цель: Доведение качества перевода low-resource языков до коммерческого уровня и обеспечение стабильности под нагрузкой.*

### Подзадача 5.1: Пайплайн LoRA Fine-Tuning для NLLB
- **Инструменты:** `peft`, `transformers`, `datasets`.
- **Реализация:** 
  - Скрипт для еженедельной выгрузки пар "Оригинал клиента" → "Исправленный перевод оператора" (из тех случаев, когда оператор вручную правил текст AI в amoCRM).
  - Форматирование этих данных в JSONL и запуск дообучения (LoRA) модели NLLB-200 для адаптации к специфическому синтаксису и сленгу мигрантов именно вашей компании.
  - Разделение данных по каналам: если большинство диалогов идет через MAX, модель будет лучше адаптирована к стилю общения в MAX.
- **Действие:** Настройка автоматического пайплайна, который раз в месяц обновляет веса модели и деплоит новую версию через Canary Release.

### Подзадача 5.2: Сквозная наблюдаемость (Observability)
- **Инструменты:** OpenTelemetry SDK, Prometheus, Grafana.
- **Реализация:** 
  - Инструментация Celery-задач: создание span-ов для каждого этапа (`lang_detect`, `asr`, `translate`, `crm_update`).
  - Расчет метрик с разбивкой по каналам:
    - `translation_latency_seconds{channel="max"}` (histogram).
    - `translation_errors_total{channel="vk"}` (counter).
    - `active_conversations{channel="telegram"}` (gauge).
  - Настройка дашборда в Grafana с фильтрами по каналам.
- **Действие:** Настройка алертов в Alertmanager: "P95 Latency > 2.0s", "NLLB OOM Error", "amoCRM Circuit Breaker Open", "MAX API Rate Limit Exceeded".

### Подзадача 5.3: Масштабирование и Нагрузочное тестирование
- **Инструменты:** Locust, KEDA (Kubernetes Event-driven Autoscaling) или Celery Autoscale.
- **Реализация:** 
  - Написание сценариев Locust для каждого канала:
    - `max_scenario.py`: эмуляция webhook-ов от MAX с учетом их rate limits.
    - `vk_scenario.py`: эмуляция событий от VK API.
    - `telegram_scenario.py`: эмуляция webhook-ов от Telegram.
  - Настройка правил KEDA для автоматического добавления подов с Celery-воркерами, когда длина очереди `translate_text_queue` превышает 50 сообщений.
  - Тестирование смешанной нагрузки: 60% MAX, 25% VK, 15% Telegram (примерное распределение).
- **Действие:** Проведение стресс-теста, валидация того, что при пиковой нагрузке система не падает, а задержки остаются в пределах SLA, а старые сообщения корректно обрабатываются или уходят в DLQ (Dead Letter Queue).
